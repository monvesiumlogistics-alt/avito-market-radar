## 1. Executive Summary

**Бизнес.** Пользователь — посредник Китай → Россия «под заказ», маржа 10–50 тыс. ₽ на позицию. Avito для него
не магазин, а **датчик спроса**. Ему нужен ежедневный ответ «что происходит на рынке и что исследовать сегодня»,
за 5–10 минут в Telegram вместо часов ручного листания.

**Главная проблема текущей системы.** Бот **не помнит рынок**: каждый прогон смотрит выдачу с нуля, хранит только
находки выше порога и последний срез категории. Без истории нельзя сказать «что изменилось», а это и есть
продукт. Вторая проблема — бюджет: ~600–900 загрузок в день с домашнего IP, и сейчас они тратятся одинаково
на мёртвые и живые категории.

**Позиция.** Не строить «ML-радар». Строить **экономный радар с памятью**:
1. Хранить каждое увиденное объявление **одной строкой** + события изменений (а не снимки).
2. Брать максимум с каждой загрузки (общее число объявлений категории лежит на странице выдачи бесплатно,
   а сейчас выбрасывается).
3. Листать **инкрементально**: глубина по темпу категории, стоп по уже известным id.
4. Карточки открывать **по квотам**, обязательно с базовой линией категории → **Attention Multiple**
   (во сколько раз объявление интереснее нормы своей категории).
5. Тренды — робастная статистика + **coverage + confidence**; сложность растёт вместе с историей.
6. **Сначала проверить официальную «Аналитику спроса» Avito** — она даёт спрос по категориям
   (просмотры, **контакты**, продавцы, объявления, цены), который мы скрейпингом меряем хуже и дороже.

**Отчёт** — одно утреннее сообщение «MARKET RADAR» с честной пометкой о покрытии и уверенности.
Существующие `/report /top /export /price /skip` и мониторинг сохраняются.

## 2. Problems in current system

| # | Проблема | Доказательство | Последствие |
|---|---|---|---|
| P1 | Нет истории рынка | `categories.last_*` перезаписывается (`market.py:_save`); выдача не сохраняется | Нельзя посчитать рост, новые модели, исчезновения |
| P2 | Бесплатные данные выбрасываются | `page-title/count` есть в фикстурах («17 888»), парсер не читает; заголовки/цены/id 50 карточек на странице не пишутся в БД | Потеря главного ряда предложения |
| P3 | Фиксированная глубина 5 стр. | `REPORT_MAX_PAGES=5` | В больших категориях — часы, не неделя («Не вся неделя»); в маленьких — лишние загрузки до 7-дневной границы каждый раз |
| P4 | Фиксированный выбор карточек | ≤12 на подкатегорию, первые группы | Нет базовой линии категории → абсолютный порог `VPD_MIN=50` одинаков для колясок и аккордеонов |
| P5 | «Продавцы» не считаются | в выдаче продавец есть только у магазинов (15/50 в фикстуре) | Нельзя отличить «60 продавцов» от «1 магазин» |
| P6 | «Ушло» = продано | `gone_at` при перепроверке; маркеры «снято» не проверены на живом Avito (ADR-010) | Ложный сигнал продаж |
| P7 | Нет телеметрии расходов | `crawl_runs.loads` одним числом | Не видно, куда ушёл бюджет |
| P8 | Нет расписания | только кнопка | Пропуски дней → дыры в истории |
| P9 | Мелочь: пустая страница = «вся неделя покрыта» | `_collect`: 0 карточек → `full=True` → `covered=7` | При смене вёрстки покрытие завышается (предлагаю фикс в Фазе 1, отдельным коммитом) |

Что **не** проблема (не трогать ради красоты): размер `market.py`/`market_logic.py` сам по себе; aiogram;
SQLite; Playwright-профиль; ручная капча; стиль сообщений.

## 3. Research findings (выжимка; ссылки — в `deep-research.md`)

1. **Официального API для чужих объявлений нет**; API для бизнеса даёт статистику только своих объявлений.
2. **«Аналитика спроса» Avito** (кабинет, обновлена 07.2025): по категории/запросу/региону — просмотры,
   контакты, конверсия, продавцы, объявления, средняя цена, 7/30 дней, динамика. Доступ — бесплатно/при пакете
   услуг (источники расходятся). API нет. **Проверить у пользователя — Фаза 0.**
3. Open source: зрелые **мониторы** (ai-goofish-monitor 14.6k★ MIT, parser_avito ~755★ без лицензии), но
   **радара спроса нет ни у кого**. Брать паттерны: история цен/событий в SQLite, «снимок + события».
   Их антиблок-механики (прокси-пулы, ротация аккаунтов) — не для нас.
4. Инкрементальный обход: частота посещения ∝ темпу изменений (Cho & Garcia-Molina); стоп по дубликатам —
   только в связке со счётчиком/датой; «stop when dry».
5. Тренды на коротких рядах: median/MAD (modified z, порог 3.5), пуассоновский тест для малых счётчиков,
   EWMA, позже CUSUM и поправка на день недели. Prophet/STL/ruptures/river — не нужны.
6. Модели товара: нормализация + модельные токены + RapidFuzz решают большую часть; эмбеддинги хуже различают
   «U2» и «U3» — не сразу.
7. Исчезновение ≠ продажа; survival analysis (Kaplan-Meier) возможен позже, если хранить first/last_seen/gone.
8. Картинки (pHash) — сильный признак дублей/relisting (Kaggle Avito Duplicates), позже, только для кандидатов.
9. SQLite хватит с запасом на годы при нашем объёме.

## 4. Proposed architecture

```
 Telegram ── /report, /radar, кнопки ──┐            APScheduler: 09:00 + catch-up при старте
                                       ▼                         │
                         ┌──────────── DailyRun (один на день, lock, checkpoint) ─────────────┐
                         │  1. SWEEP  (выдача, ~55–65% бюджета)                                │
                         │  2. DEEP   (карточки, ~35–45%: sampler по квотам)                   │
                         │  3. AGGREGATE (0 загрузок)  →  4. DETECT (0)  →  5. REPORT (0)       │
                         └─────────────────────────────────────────────────────────────────────┘
                                       │ все загрузки через существующие
                                       ▼ BrowserGate / AvitoProvider / wait_unblocked / budget
 Хранилище SQLite:
   ad, ad_event, card_obs              ← сырые наблюдения (память рынка)
   scan, scan_category                 ← прогоны, чекпойнт, телеметрия
   category_day, model_day             ← дневные агрегаты (пересчитываемые)
   signal                              ← события детекторов (что попало в отчёт)
   (существующие) categories, finds, crawl_runs, watch_rules, listings — без изменений
```

**Модули** (минимум новых файлов, логика — чистые функции):

| Файл | Что | I/O |
|---|---|---|
| `app/services/sweep.py` | инкрементальный обход выдачи, запись `ad`/`ad_event`/`scan_category` | да |
| `app/services/sampler.py` | выбор карточек по квотам | нет (чистый) |
| `app/services/radar_logic.py` | агрегаты дня, детекторы, confidence/coverage, форматирование отчёта | нет (чистый) |
| `app/services/products.py` | нормализация заголовка → `model_key`, кластеризация RapidFuzz | нет (чистый) |
| `app/services/radar.py` | DailyRun: оркестрация шагов 1–5, расписание/catch-up | да |

Общий для `/report` и sweep код (бюджет, `_fetch`, капча, передача браузера, прогресс) выносится из
`MarketCrawler` в небольшой `CrawlSession` **в начале Фазы 2** — когда у него появляется второй потребитель,
не раньше. Существующие тесты `/report` — страховка рефакторинга.

## 5. Data model

> **Реализовано в Фазе 1** (ADR-015) в упрощённом виде: `ads`, `ad_events`, `card_obs`, `scan_categories`
> (роль `scan` играет существующая `crawl_runs`); `category_day`, `model_day`, `signal` — в Фазе 3+.

Принцип: **одна строка на объявление + события изменений**, а не снимок на каждую встречу.
Снимки нужны только там, где величина непрерывно меняется и её дельта — сигнал (просмотры карточки).

```sql
-- Объявление: текущее состояние. Upsert при каждой встрече в выдаче.
CREATE TABLE ad (
  id            INTEGER PRIMARY KEY,          -- avito item id (числом: монотонность, водяной знак)
  category_id   INTEGER NOT NULL REFERENCES categories(id),
  title         TEXT NOT NULL,
  model_key     TEXT,                         -- products.normalize(); NULL = не модельный товар
  price         INTEGER,
  url_path      TEXT NOT NULL,                -- без query (?context=... — мусор)
  city          TEXT,
  shop          TEXT,                         -- имя магазина, если есть в выдаче (частник = NULL)
  seller_id     TEXT,                         -- из карточки (deep), NULL пока не открывали
  image_url     TEXT,                         -- для pHash позже
  posted_at     TIMESTAMP,                    -- лучшая известная дата (выдача → карточка → профиль)
  posted_src    TEXT,                         -- search | card | seller
  first_seen_at TIMESTAMP NOT NULL,
  last_seen_at  TIMESTAMP NOT NULL,           -- последний раз видели в выдаче
  promoted_seen INTEGER NOT NULL DEFAULT 0,   -- сколько раз видели как промо
  status        TEXT NOT NULL DEFAULT 'live', -- live | reserved | sold | removed | expired | relisted | unknown_gone
  status_at     TIMESTAMP,
  relist_of     INTEGER                        -- id предыдущего объявления, если распознан relisting
);
CREATE INDEX ix_ad_cat_first ON ad(category_id, first_seen_at);
CREATE INDEX ix_ad_model     ON ad(model_key, first_seen_at) WHERE model_key IS NOT NULL;
CREATE INDEX ix_ad_status    ON ad(status, last_seen_at);

-- Изменения: только когда что-то поменялось (цена, статус, заголовок).
CREATE TABLE ad_event (
  ad_id INTEGER NOT NULL, at TIMESTAMP NOT NULL,
  kind  TEXT NOT NULL,        -- price | status | title
  old   TEXT, new TEXT,
  PRIMARY KEY (ad_id, at, kind)
);

-- Замер карточки (дорогой). Несколько замеров одного объявления → скорость просмотров.
CREATE TABLE card_obs (
  ad_id INTEGER NOT NULL, at TIMESTAMP NOT NULL, scan_id INTEGER,
  views INTEGER, today INTEGER,
  bucket TEXT NOT NULL,       -- baseline | model | new_model | exploit | explore | recheck | report
  PRIMARY KEY (ad_id, at)
);

-- Прогон и чекпойнт.
CREATE TABLE scan (
  id INTEGER PRIMARY KEY, kind TEXT NOT NULL,        -- daily | report
  day DATE NOT NULL, started_at TIMESTAMP, finished_at TIMESTAMP,
  status TEXT NOT NULL,                              -- running | blocked | budget | done | failed | interrupted
  budget INTEGER, telemetry TEXT                      -- JSON, см. §14
);
CREATE TABLE scan_category (
  scan_id INTEGER, category_id INTEGER,
  status TEXT,                -- pending | done | error | skipped
  pages INTEGER, cards_seen INTEGER, new_ads INTEGER, known_ads INTEGER,
  total_count INTEGER,        -- «17 888» со страницы выдачи (с pmin)
  window_hours REAL,          -- какой промежуток времени покрыт прочитанными страницами
  stop_reason TEXT,           -- known_ratio | watermark | age_limit | depth_cap | empty | budget
  PRIMARY KEY (scan_id, category_id)
);

-- Дневной агрегат категории. Пересчитывается из ad/card_obs/scan_category (идемпотентно).
CREATE TABLE category_day (
  category_id INTEGER, day DATE,
  total_count INTEGER,                    -- предложение «на полке»
  new_ads INTEGER, new_ads_est REAL,      -- точно увиденные / оценка с поправкой на покрытие
  coverage REAL,                          -- 0..1: доля суток, покрытая выдачей
  shops_share REAL,
  price_p25 INTEGER, price_p50 INTEGER, price_p75 INTEGER,
  sampled INTEGER,                        -- карточек baseline за последние 7 дней
  vpd_p50 REAL, vpd_p75 REAL,             -- базовая линия внимания (робастная)
  models_active INTEGER, models_new INTEGER,
  demand_views INTEGER, demand_contacts INTEGER,  -- из «Аналитики спроса», если будет доступ (иначе NULL)
  PRIMARY KEY (category_id, day)
);

CREATE TABLE model_day (
  model_key TEXT, category_id INTEGER, day DATE,
  ads INTEGER, new_ads INTEGER, cities INTEGER, sellers_known INTEGER, shops INTEGER,
  price_p50 INTEGER, am_p50 REAL,         -- медианный Attention Multiple открытых карточек
  PRIMARY KEY (model_key, category_id, day)
);

-- Что детекторы нашли (и что ушло в отчёт) — для разбора «почему бот так сказал».
CREATE TABLE signal (
  id INTEGER PRIMARY KEY, day DATE, kind TEXT,  -- category_state | emerging_model | attention_outlier | price_move | oversupply
  entity TEXT, metrics TEXT /* JSON */, confidence REAL, reported INTEGER DEFAULT 0
);
```

**Решение «снимки или изменения» — изменения.** Встреча объявления в выдаче обновляет `last_seen_at`
(и `promoted_seen`); цена пишется в `ad_event` только при изменении. Полный снимок каждой встречи дал бы
~×5–10 строк без новой информации. Позиция в выдаче не хранится (бесполезна: сортировка по дате).

⚠ исправление аудита: `category_daily.disappeared` из sweep — **убрано**. Мы читаем только верх выдачи; объявление
выпадает из окна от старения, а не от продажи. Исчезновения определяются только перепроверкой карточек (`recheck`).
⚠ `unique_sellers` по выдаче — **убрано**: частники в выдаче анонимны. Вместо: `shops_share` (из выдачи),
`cities` (прокси независимости), `sellers_known` (из открытых карточек).

## 6. Crawl strategy

**Information per load (IPL)** — главный принцип. Перед каждой загрузкой: «что новое я узнаю?».

| Загрузка | Что даёт | IPL |
|---|---|---|
| Страница выдачи | до 50 объявлений (id, title, price, city, shop, дата, фото) + `total_count` категории | высокая, пока на странице есть новые id |
| Страница выдачи, где всё уже известно | только `last_seen` | ≈0 → стоп |
| Карточка | views, today, точная дата, продавец, статус | 1 объявление, но единственный источник внимания |
| Профиль продавца | реальная дата 1 объявления (+ список его объявлений) | низкая; только для кандидатов в отчёт |
| Главная (warm-up) | ничего | обязательный накладной расход, 1 раз |

Правила:
1. **Не открывать** карточку: замеренную < 20 ч назад (кроме recheck), промо, цена < `MIN_PRICE`,
   старше 7 дней, копию уже замеренной группы (заголовок+цена+магазин).
2. **Профиль продавца** — только для объявлений, которые иначе попадут в отчёт с неточной датой.
3. **Частота категории**: тихие (оценка < 25 новых/сутки) — раз в 2 дня; остальные — ежедневно.
4. Одна страница выдачи всегда даёт `total_count` → даже «тихий» день категории стоит 1 загрузку.

## 7. Sweep algorithm

> **Фаза 0:** гипотеза «id монотонны» **опровергнута** (корреляция id и даты 0.02 на 35 объявлениях) —
> водяной знак id ниже не используется; стоп только по доле известных + 7 дней + глубина.

```
for category in order(categories):                    # порядок: давно не были → высокий темп → остальные
    if quiet(category) and visited_yesterday: mark skipped; continue
    est = rate_per_hour(category) * hours_since_last_sweep     # по истории; нет истории → max_pages_first=3
    depth_cap = clamp(ceil(est / 50 * 1.3) + 1, 1, 10)
    watermark = max ad.id категории, увиденный в прошлом sweep (если id монотонны — Фаза 0)
    for page in 1..depth_cap:
        cards, total = fetch_search(category, page)            # s=104, pmin
        checkpoint(scan_category: page, counts)                # переживает капчу/рестарт
        nonpromo = [c for c in cards if not promo(c)]
        upsert ad (first_seen / last_seen / price events)
        known_ratio = share(nonpromo already in ad before this scan)
        if not cards: stop("empty")                            # P9: coverage считается по факту, не =7 дней
        if oldest(nonpromo).posted_at < now - 7d: stop("age_limit")
        if page >= 1 and known_ratio >= 0.85: stop("known_ratio")
        if watermark and max(id in nonpromo) < watermark: stop("watermark")
    else: stop("depth_cap")  → coverage < 1, new_ads_est = seen / coverage
```

Защита от ложного стопа:
- промо и «поднятые» объявления (старый id наверху) не входят в `known_ratio` / не сдвигают водяной знак;
- стоп по `known_ratio` только после чтения страницы **целиком**;
- первая встреча категории (истории нет) → без инкрементального стопа, только 7 дней/`depth_cap`;
- если после стопа `new_ads` на последней странице > 30% — следующий день глубина +2 (самокоррекция).

Темп категории: `rate = new_ads / window_hours` по последним 7 sweep (медиана) — оценка в духе
Cho & Garcia-Molina; хранится в `scan_category`, отдельная таблица не нужна.

**Coverage**: `window_hours` = время от самого старого прочитанного непромо-объявления до момента sweep
(с точностью, которую даёт дата; уточняется id-калибровкой, если гипотеза подтвердится); `coverage =
min(1, window_hours / hours_since_last_sweep)`.

## 8. Deep scan sampler

Бюджет карточек `D` = остаток дневного бюджета после sweep. Квоты (неиспользованное перетекает дальше):

| Корзина | Доля | Что | Зачем |
|---|---|---|---|
| **baseline** | 30% | случайные свежие (1–7 дн) объявления категорий, у которых `sampled_7d < 15`; ротация | знаменатель Attention Multiple; без неё нет сравнения категорий |
| **models** | 25% | модели с ≥3 объявлениями или кандидаты discovery: по 1–2 карточки, разные продавцы | подтвердить «несколько независимых продавцов», внимание к модели |
| **recheck** | 15% | объявления с высоким AM 1–14 дней назад | Δviews/Δt (текущая скорость), статус (продано/забронировано/снято) |
| **exploit** | 20% | новые объявления в категориях с высоким вниманием/👍 | находки как сейчас (`/report`) |
| **explore** | 10% | категории, где давно/мало мерили | не застрять в известном |

Внутри корзины — простой приоритет (свежесть, цена ≥ порога, не копия). В V2 (≥14 дней данных) выбор
**категорий** в exploit/explore — Thompson sampling: Beta(успехи+1, неудачи+1), где успех = карточка с AM ≥ 3.
Это ~30 строк, без библиотек.

Существующий `/report` становится **ручным запуском deep-части** (exploit + recheck) с текущим форматом
находок — пользователь ничего не теряет.

## 9. Product normalization

`products.normalize(title, category) -> model_key | None`:
1. lower, `ё→е`, убрать эмодзи/пунктуацию, транслит кириллических написаний брендов по словарю алиасов.
2. Удалить стоп-слова: общие («новый», «оригинал», «в наличии», «доставка», «под заказ») и **слова категории**
   (токены, встречающиеся в > 30% заголовков категории: «электровелосипед», «коляска»).
3. Склеить буквенно-цифровые хвосты: `u2 pro`→`u2pro`, `48 v`→`48v`; размеры/объёмы/напряжение вынести
   в атрибуты (не часть ключа модели).
4. Ключ = бренд (если распознан) + модельные токены (буквы+цифры, ≥2 символа; расширение существующего
   `model_key`). Нет модельных токенов → `NULL` (товар не модельный: «гармонь»).
5. Склейка вариантов: внутри категории RapidFuzz `token_set_ratio ≥ 90` между ключами + медианы цен в пределах ×1.5
   → union-find → канонический ключ (самый частый вариант).

Словарь брендов растёт **из данных**: латинский токен, встретившийся у ≥3 разных городов/магазинов за 14 дней,
предлагается как бренд (в лог, без участия пользователя).

**Discovery нового кластера** (signal `emerging_model`): ключ, у которого за 14 дней ≤ 2 объявлений, а за последние
3 дня ≥ 5, в ≥ 3 городах или ≥ 3 известных продавцах, пуассоновский p < 0.01 против фона. Кандидаты автоматически
получают карточки из корзины `models` (подтверждение продавцов и внимания).

Эмбеддинги (BGE-M3/E5) — только если ручная разметка 100 пар покажет recall < 80%.

## 10. Trend detection

Прогрессия по длине истории (`history_days` категории):

| История | Метод | Что разрешено говорить |
|---|---|---|
| 1–6 дней | сравнение с первым днём; пуассоновский тест для счётчиков; абсолютные минимумы (≥ 10 новых/сутки) | только «новое на рынке» (emerging models), «внимание ×N к норме» при `sampled ≥ 15`; состояния категорий — `UNKNOWN` |
| 7–13 дней | rolling median + MAD (modified z = 0.6745·(x−med)/MAD), EWMA(α=0.3) | GROWING / COOLING с confidence ≤ MEDIUM |
| 14–29 | + отношение коротких/длинных EWMA (ускорение), устойчивость ≥ 2 дня подряд | все состояния, HIGH возможен |
| 30+ | + CUSUM (медленный рост), поправка на день недели (медиана по тому же дню) | — |
| 60+ | Kaplan-Meier времени до `sold/reserved/removed` для топ-моделей (lifelines) | «ликвидность» модели |

Метрики категории (из `category_day`):
- **Supply velocity** = `new_ads_est` в сутки; **Supply stock** = `total_count`.
- **Attention level** = `vpd_p50` (baseline), **Attention per listing** = `vpd_p50`; если доступна «Аналитика
  спроса» — `demand_views / total_count` и `demand_contacts / total_count`.
- **Demand/Supply** = z(attention) − z(supply velocity).
- **Price signal** = изменение `price_p50` и сжатие `p75/p25`.

Состояния (только при confidence ≥ MEDIUM, иначе `UNKNOWN`):

| Состояние | Правило (z — modified z к 14-дневной истории) |
|---|---|
| EMERGING | категория была тихой (supply < p25 своей 30-дн. истории) и z_supply ≥ 3, z_att ≥ 2 |
| GROWING | z_supply ≥ 2 или z_att ≥ 2, ни одно не ≤ −1, ≥ 2 дня подряд |
| HOT | `vpd_p50` в верхних 10% категорий и стабильно (|z| < 2) |
| OVERSUPPLIED | z_supply ≥ 2 и z_att ≤ 0 (предложение растёт быстрее внимания) |
| COOLING | z_supply ≤ −2 или z_att ≤ −2 |
| STABLE | иначе |

**Attention Multiple** объявления/модели:
`AM = vpd / baseline_c`, где `baseline_c = (n·med_c + k·med_section) / (n + k)`, k = 5 —
медиана категории, «стянутая» к медиане раздела при малой выборке (empirical Bayes, защита от 3 карточек).
Возраст учитывается: vpd считается только для объявлений старше 12 ч (свежие получают бонусный показ),
для младше — используется `today`. В V2 — базовые линии по корзинам возраста (0–1, 1–3, 3–7 дней).
Пример: медиана категории 10 → объявление 50 = **5×**; медиана 150 → 50 = **0.3×** (слабо).

## 11. Confidence calculation

Каждый сигнал несёт `confidence ∈ [0,1]` и метку:

```
conf = min(
  n_factor       = min(1, n / n_required),          # n_required: 15 карточек baseline, 10 объявлений модели
  history_factor = min(1, history_days / 14),
  coverage       = средний coverage за окно,
  seller_factor  = min(1, independent / 3),         # продавцы/города; для категорий = 1
) * persistence                                      # 1.0 если сигнал 2+ дня подряд, иначе 0.8
HIGH ≥ 0.7, MEDIUM ≥ 0.4, LOW < 0.4
```

Правила вывода: в основные разделы отчёта — только MEDIUM+; LOW — в строку «наблюдаю» без громких слов.
Никаких «взорвалась» при n < 10. `min()` намеренно: одно слабое звено = слабый вывод.

## 13. Scheduler

- APScheduler `cron 09:00 МСК`, `max_instances=1`, `coalesce=True`, `misfire_grace_time=6h`.
- **Catch-up при старте**: если в `scan` нет `kind='daily'` за сегодня со статусом `done` → через 2 мин после
  запуска бота продолжить/начать (ПК включили в 13:00 — прогон в 13:02).
- **Lock**: существующий `BrowserGate` + проверка `scan.status='running'` (с `mark_interrupted` при старте, как сейчас).
- **Checkpoint**: `scan_category` (страница, счётчики) — после рестарта/капчи продолжается с недоделанной
  категории; данные уже записанных страниц не теряются (в отличие от текущего «подкатегория заново»).
- **Блок/капча** (без обхода): сохранить прогресс → «🧩» в Telegram → ждать человека `CAPTCHA_WAIT_MINUTES` →
  продолжить; timeout → `scan.status='blocked'`, отчёт строится по собранному с пометкой покрытия,
  кнопка «Продолжить».
- Отчёт отправляется после шага 5 даже при `budget`/`blocked` (с честным покрытием).

## 14. Performance model

Измерено: ~6–10 загрузок/мин; безопасный дневной объём с домашнего IP — **~600–900** (не 2 000).
Конфиг: `RADAR_DAILY_BUDGET=800`.

| Шаг | Загрузок/день | Комментарий |
|---|---|---|
| warm-up, накладные | ~5 | |
| Sweep, первые 1–3 дня (истории нет) | 209 × ~3 ≈ 600 | первые дни — в основном sweep; deep минимальный |
| Sweep, установившийся | ~300–450 | ~120 тихих категорий × 0.5 (раз в 2 дня) + ~90 × 1–2 стр. + ~10 крупных × 5–10 |
| Deep | остаток ≈ 350–500 | 30% baseline ≈ 120 карточек/день → каждая категория получает 15 замеров примерно за неделю ротации |
| Профили продавцов | ≤ 20 | только кандидаты отчёта |
| **Итого** | ≈ 800 ≈ 1.5–2 ч | один прогон в день |

**Телеметрия** (`scan.telemetry` JSON + строка в итоге): `sweep_pages, deep_cards, recheck_cards,
profile_pages, captcha_waits, block_minutes, errors, known_ads, new_ads, duplicates_skipped,
stop_reasons{...}, ipl_sweep = new_ads / sweep_pages, ipl_deep = signals / deep_cards`.
IPL позволяет видеть, какие категории «пустые» и тратят бюджет зря.

## 15. Storage growth

Строка `ad` ≈ 350 Б + индексы ≈ 450 Б. `card_obs` ≈ 40 Б. `ad_event` ≈ 60 Б.

| Новых объявлений/день | 30 дней | 90 дней | 1 год |
|---|---|---|---|
| 10k | 135 МБ | 0.4 ГБ | 1.6 ГБ |
| 20k (наш реалистичный максимум при 400 стр. sweep) | 270 МБ | 0.8 ГБ | 3.3 ГБ |
| 50k | 0.7 ГБ | 2 ГБ | 8 ГБ |
| 100k | 1.4 ГБ | 4 ГБ | 16 ГБ |

`card_obs` (~500/день) и агрегаты — единицы МБ в год. Для сравнения: снимок каждой встречи
(~25k встреч/день × ~80 Б) добавил бы ~0.7 ГБ/год без новой информации — поэтому изменения, а не снимки.

SQLite: один писатель (у нас один процесс), WAL-режим для чтения команд во время прогона, < 1 ТБ — по
рекомендации sqlite.org подходит «почти всегда». **PostgreSQL нужен**, только если: несколько процессов пишут
одновременно, внешний дашборд/мультиюзер, или БД > ~50 ГБ. Ничего из этого не планируется.
Гигиена: `PRAGMA journal_mode=WAL`, `VACUUM` раз в месяц, архив `ad` со `status != live` старше 180 дней —
по желанию, не раньше чем через полгода.

## 17. Testing strategy

Сохранить 200 существующих тестов зелёными на каждом шаге. Каждая фаза: тест → код → регрессия.

| Что | Как |
|---|---|
| Парсер `total_count`, `shop`, id | существующие фикстуры (`market_search_s104.html` = 17 888) |
| Стоп-эвристика | синтетические страницы: промо наверху, «поднятое» старое объявление, перемешанные id, пустая страница, первая встреча категории |
| Upsert/events | in-memory SQLite: повторная встреча не создаёт строк, изменение цены → 1 событие |
| Checkpoint/resume | FakeProvider бросает ProviderBlocked на N-й загрузке → продолжение с той же страницы |
| Sampler | чистая функция: квоты, перетекание остатка, исключения (замерено < 20 ч, промо, копии) |
| Нормализация | таблица пар «должны склеиться / не должны» (Aimiko U2 Pro ≡ AIMIKO U2PRO 48v; U2 ≠ U3) |
| Детекторы | синтетические ряды: плоский + выброс, плавный рост, мало данных → UNKNOWN, малые счётчики → нет ложной тревоги |
| Confidence | граничные случаи: n=3 → LOW при любом росте |
| Отчёт | длина по `tg_len` ≤ 4096, LOW не попадает в основные разделы, премиум on/off |
| Расписание | catch-up: нет daily сегодня → запуск; есть done → нет; running → не дублировать |
| Регрессия | `/report /top /export /price /skip`, мониторинг — существующие тесты без изменений |
