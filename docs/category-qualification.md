# Category Qualification — дизайн

Дата: 2026-10-04. Статус: **предложение, ждёт подтверждения**. Product Deep Scan (Фаза 4) — после этого.
Связано: `radar-v2-design.md`, `avito-traffic-v2.md` (ADR-019: потолок 450 загрузок/сутки).

Цель: широкий обход — **временный** механизм поиска рынков. Из ~257 категорий (209 обычных + 48 «бренд × пол»)
отобрать **10–15 CORE** и **15–25 WATCH**, где системно находятся товары под закупку в Китае с маржой 10–50 тыс. ₽,
и тратить на них основной бюджет. Цель после отбора — **120–200 загрузок в сутки**, а не 450.

---

## 1. Что у нас реально есть (данные и их ограничения)

| Сигнал | Источник | Цена | Ограничение |
|---|---|---|---|
| Новых в сутки, темп | `scan_categories` (sweep) | 0 доп. | у огромных категорий — оценка по плотности 1-й страницы |
| Всего объявлений «на полке» | `total_count` с 1-й страницы | 0 | с фильтром `pmin` |
| Цены p25/p50/p75 | `ads.price` | 0 | |
| Повторяемость моделей | `ads.model_key` | 0 | только латинские модели (бренд+код); «гармонь» без модели |
| Города | первый сегмент `ads.url_path` | 0 | прокси независимости продавцов |
| Магазины | `ads.shop` (имя в выдаче) | 0 | **частники в выдаче анонимны** |
| Продвинутые | `ads.promoted_seen` / промо на странице | 0 | нужен счётчик в `scan_categories` |
| **Просмотры (спрос)** | **карточка** → `card_obs` | **1 загрузка на объявление** | главный расход |
| Независимые продавцы | `seller_url` из карточки | вместе с просмотрами | только по выборке |
| Исчезновение (ликвидность) | повторное открытие карточки через N дней | 1 загрузка | «снято» ≠ «продано»; маркеры не проверены (ADR-010) |

Вывод: **дешёвый слой** (без карточек) даёт предложение, цену, повторяемость, разнообразие. **Спрос** — только
выборкой карточек, поэтому её получают не все категории, а кандидаты.

## 2. CategoryMetrics (хранятся отдельно, без «магического» итогового балла)

Ежедневный снимок на категорию — пересчитывается из истории, **0 загрузок**.

| Измерение | Поля | Как считается |
|---|---|---|
| **SUPPLY** | `new_per_day`, `supply_growth`, `total_count`, `promo_share`, `coverage`, `mode` | темп — как в радаре (ADR-017); рост — темп / медиана 14 дн; промо — промо / непромо на прочитанных страницах |
| **TICKET** | `price_p25`, `price_p50`, `price_p75` | объявления за 7 дн |
| **REPEATABILITY** | `model_share`, `models_repeated`, `top_model_share` | доля объявлений с `model_key`; моделей с ≥ 3 объявл. в ≥ 2 городах; доля самой частой модели (≫ 30% — рынок одной модели) |
| **DIVERSITY** | `cities_per_100`, `shop_share`, `top_shop_share`, `sellers_sampled` | разных городов на 100 объявлений; доля объявлений магазинов; доля крупнейшего магазина; разных продавцов в выборке карточек |
| **DEMAND** | `sampled_n`, `vpd_p50`, `vpd_p75`, `vpd_p90`, `attention_growth` | baseline-выборка карточек за 14 дн (возраст 1–4 дн, цена ≥ `MIN_PRICE`); vpd = просмотры / возраст; рост — p50 сейчас против p50 7 дн назад |
| **COMPETITION** | `attention_per_listing` | `vpd_p50` / log(1 + `new_per_day`) — спрос на одно объявление с поправкой на поток |
| **LIQUIDITY** | `gone_7d_share` (позже `km_median_days`) | доля выборки, исчезнувшей за 7 дн (только CORE/WATCH, перепроверка) |
| **SOURCEABILITY** | `source_score` = NULL | заглушка до China-фазы |
| **CONFIDENCE** | `conf_supply`, `conf_demand` | по объёму, длине истории, покрытию (как ADR-017); спрос: `sampled_n` ≥ 15 → HIGH, 8–14 → MEDIUM, < 8 → LOW |

Каждое измерение дополнительно получает **уровень LOW / MID / HIGH** по процентилю среди категорий, у которых оно
измерено (робастно, без абсолютных порогов между разными рынками). Исключение — TICKET: абсолютный порог по бизнесу.

**Attention Multiple (AM)** для товаров = vpd объявления / `vpd_p50` его категории, при малой выборке медиана
«стягивается» к медиане раздела: `(n·med_cat + 5·med_section) / (n + 5)`.

## 3. Tiers

`CORE` · `WATCH` · `EXPLORE` · `LOW_PRIORITY`. Внутри EXPLORE флаг **`candidate`** — категория прошла дешёвый фильтр
и получает выборку карточек.

### 3.1. Дешёвый фильтр (только поиск, дни 1–3)

Сразу в **LOW_PRIORITY** (с причиной):
- `price_p50` < `TICKET_MIN` (по умолчанию **15 000 ₽**) — не наша экономика;
- `new_per_day` < 2 при `conf_supply` ≥ MEDIUM — мёртвый рынок;
- `top_shop_share` > 60% — рынок одного магазина.

Остальные ранжируются по **дешёвому приоритету**, который используется **только для выбора, кому дать карточки**:
`cheap = pct(price_p50 в диапазоне 15–300k) + pct(models_repeated) + pct(cities_per_100) + pct(log new_per_day)`.
Топ **~55** → `candidate = true`.

### 3.2. Выборка спроса (кандидаты, дни 3–8)

Каждому кандидату — **3 карточки в сутки** из уже известных по выдаче объявлений (`ads`, возраст 1–4 дн,
случайно, разные города/магазины). За 5 дней ≈ 15 карточек → `conf_demand` HIGH.

### 3.3. Правила tiers (объяснимые, по измерениям)

| В tier | Условие (все пункты) |
|---|---|
| **CORE** | TICKET ок · DEMAND HIGH (`vpd_p50` в верхних 30% измеренных **и** `vpd_p75` ≥ `CORE_MIN_P75`) · REPEATABILITY ≥ MID · DIVERSITY ≥ MID · `conf_demand` ≥ MEDIUM |
| **WATCH** | TICKET ок · DEMAND ≥ MID **или** (DEMAND ещё не измерен и `cheap` в верхних 25%) |
| **LOW_PRIORITY** | дешёвый фильтр **или** DEMAND LOW при `conf_demand` ≥ MEDIUM два пересчёта подряд |
| **EXPLORE** | всё остальное (мало данных) |

Если в CORE проходит больше `CORE_MAX` (15) — оставить лучших по `vpd_p50 × attention_per_listing`, остальные в WATCH.
Аналогично `WATCH_MAX` (25). Числа — потолки, а не план: если сильных 8 — CORE будет 8.

### 3.4. Гистерезис (чтобы не прыгало)

| Переход | Нужно |
|---|---|
| EXPLORE → WATCH | условие WATCH выполняется **2 пересчёта подряд** |
| WATCH → CORE | условие CORE **3 пересчёта подряд**, `conf_demand` ≥ MEDIUM |
| CORE → WATCH | `vpd_p50` ниже **50-го** процентиля (не 70-го — коридор) **5 пересчётов подряд**, и в CORE не меньше **7 дней** |
| WATCH → LOW_PRIORITY | DEMAND LOW при `conf_demand` ≥ MEDIUM **5 пересчётов подряд** |
| LOW_PRIORITY → EXPLORE | рост предложения или внимания (z ≥ 2) на перепроверке **или** 30 дней без пересмотра |
| любой → LOW_PRIORITY по TICKET | сразу (бизнес-фильтр), обратно — если `price_p50` ≥ `TICKET_MIN × 1.2` (коридор) |

Счётчики подряд — `streak_up` / `streak_down` в `categories`; каждый переход пишется в `tier_events` с причиной
(«CORE: спрос p50 41/д — топ 12%, 9 моделей в ≥ 2 городах, 23 продавца в выборке»).

## 4. Ежедневный обход после отбора (план загрузок)

| Tier | Кол-во | Выдача | Карточки | Загрузок/сутки |
|---|---|---|---|---|
| CORE | ~12 | инкремент, 2–3 стр. (крупные — 1) | 5/кат.: baseline 2 + модели/новое 3 | 30 + 60 = **90** |
| WATCH | ~20 | 1 стр. | 1.5/кат., ротация | 20 + 30 = **50** |
| EXPLORE | ~15 в день из ротации (давно не виденные, новые, бывшие слабые) | 1 стр. | 0 (карточки — только если стал кандидатом) | **15** |
| LOW_PRIORITY | все, раз в 14 дн | 1 стр. | 0 | **~9** |
| Ликвидность | CORE/WATCH | — | перепроверка 10 | **10** |
| Профили | только топ «Исследовать» | — | 3 | **3** |
| Warm-up | | | | **1** |
| **Итого** | | | | **≈ 178** |

Доля разведки (EXPLORE + LOW_PRIORITY + новые кандидаты) ≈ 24 из 178 ≈ **14%** — в пределах 10–20%.
Потолок 450 (ADR-019) остаётся предохранителем; нормальный расход 150–200.

## 5. Период отбора

| Дни | Что | Загрузок/сутки | Результат |
|---|---|---|---|
| 1–3 | широкий обход всех 257 (в основном по 1 стр.) | 260–330 | SUPPLY/TICKET/REPEATABILITY/DIVERSITY для всех; ~40–60% → LOW_PRIORITY по дешёвому фильтру |
| 3–8 | выборка спроса у ~55 кандидатов (3 карт./день) + 1 стр. кандидатов + ротация остальных по 50/день | ~280–320 | `conf_demand` MEDIUM к 5–6-му дню, HIGH к 8-му |
| ~8 | **первый отбор** CORE/WATCH (MEDIUM уверенность, гистерезис уже начал считать) | | |
| 8–14 | переход на план §4, кандидатов становится меньше | 200 → 180 | |
| 14–30 | стабильный рейтинг, `attention_growth`, первые данные ликвидности | ~180 | |

Почему так, а не 7 дней: при 3 карточках в день медиана vpd категории стабилизируется после ~12–15 замеров;
быстрее — значит открывать больше карточек в день, а это прямо противоречит цели снизить нагрузку.

## 6. DB changes

```sql
ALTER TABLE categories ADD tier TEXT DEFAULT 'EXPLORE';
ALTER TABLE categories ADD tier_since DATE;
ALTER TABLE categories ADD tier_reason TEXT;
ALTER TABLE categories ADD candidate BOOLEAN DEFAULT 0;
ALTER TABLE categories ADD streak_up INTEGER DEFAULT 0;
ALTER TABLE categories ADD streak_down INTEGER DEFAULT 0;
ALTER TABLE categories ADD last_explored_at TIMESTAMP;
ALTER TABLE scan_categories ADD promo_seen INTEGER;

CREATE TABLE category_metrics (            -- снимок на день; пересчитывается, загрузок не требует
  category_id INTEGER, day DATE,
  new_per_day REAL, supply_growth REAL, total_count INTEGER, promo_share REAL, coverage REAL,
  price_p25 INTEGER, price_p50 INTEGER, price_p75 INTEGER,
  model_share REAL, models_repeated INTEGER, top_model_share REAL,
  cities_per_100 REAL, shop_share REAL, top_shop_share REAL, sellers_sampled INTEGER,
  sampled_n INTEGER, vpd_p50 REAL, vpd_p75 REAL, vpd_p90 REAL, attention_growth REAL,
  attention_per_listing REAL, gone_7d_share REAL, source_score REAL,
  conf_supply REAL, conf_demand REAL,
  PRIMARY KEY (category_id, day));

CREATE TABLE tier_events (
  id INTEGER PRIMARY KEY, category_id INTEGER, day DATE, old TEXT, new TEXT, reason TEXT);
```
`card_obs.bucket` получает `baseline` (выборка спроса) и `liquidity` (перепроверка).

## 9. Открытые вопросы к пользователю

1. `TICKET_MIN` = 15 000 ₽ по медиане категории — так? (Маржа 10–50k обычно требует чек от ~20–25k; 15k — с запасом,
   чтобы не отсечь категории, где дорогие модели есть, но медиана ниже.)
2. 48 категорий «бренд × пол» (одежда) квалифицировать вместе с остальными или отдельным списком?
3. Первый отбор на ~8-й день с уверенностью MEDIUM — ок, или ждать 14 дней?
