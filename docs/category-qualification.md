# Category Qualification — дизайн (rev. 2: successive halving)

Дата: 2026-10-04. Статус: **rev. 2 после замечаний пользователя, ждёт подтверждения**. Код не начат.
Связано: `radar-v2-design.md`, `avito-traffic-v2.md` (ADR-019: потолок 450 загрузок/сутки).

Изменения rev. 2: турнир с отсевом вместо равной выборки 55 × 15 карточек; цена — по p75 и долям дорогих
объявлений, а не по медиане; 48 срезов «бренд × пол» — отдельный тип `QUERY_WATCH`; концентрация продавца —
штраф, а не исключение; CORE не заполняется до квоты; предварительный отбор на 7–8-й день.

## 1. Вопросы, на которые отвечает отбор

| # | Вопрос | Измерение | Источник |
|---|---|---|---|
| 1 | Сколько появляется предложения? | SUPPLY: `new_per_day`, `supply_growth`, `total_count` | выдача (0 доп. загрузок) |
| 2 | Сколько внимания у типичного объявления? | DEMAND: `vpd_p50`, `vpd_p75` выборки | карточки |
| 3 | Устойчиво ли внимание? | DEMAND: разброс по дням (p50 по дням, `attention_growth`) | карточки, несколько дней |
| 4 | Как быстро исчезают объявления? | LIQUIDITY: `gone_7d_share` (позже Kaplan-Meier) | перепроверка — только финалистам |
| 5 | Есть ли повторяемые модели? | REPEATABILITY: `model_share`, `models_repeated` | выдача |
| 6 | Есть ли независимые продавцы? | DIVERSITY: `cities_per_100`, `top_shop_share`, `sellers_sampled` | выдача + карточки |
| 7 | Достаточно ли высокий чек? | TICKET: `price_p50/p75`, `share_ge_20k/30k` | выдача |
| 8 | Есть ли перспектива закупки в Китае? | SOURCEABILITY: заглушка | China-фаза |

Плюс COMPETITION (`attention_per_listing` = `vpd_p50` / log(1 + `new_per_day`)) и CONFIDENCE (отдельно по
предложению и спросу). Измерения хранятся раздельно; для перехода между стадиями — объяснимая функция ранжирования (§4).

## 2. Два типа источников

| Тип | Что | В отборе CORE | Рейтинг |
|---|---|---|---|
| `CATEGORY` | 209 настоящих подкатегорий Avito | **да** | 🏆 TOP CATEGORIES |
| `QUERY_WATCH` | 48 срезов `?q=бренд` × пол | **нет** | отдельный 👗 BRAND WATCH: темп, цены, частые модели; позже — сигналы товаров |

Почему отдельно: срезы пересекаются с категориями (те же объявления), их размер зависит от слова в запросе, а не от
рынка — сравнивать «категория против среза» некорректно.

**Нужная правка данных** (иначе срезы портят метрики категорий): сейчас `ads.category_id` = первая выдача, где
объявление увидели. Если первым был срез, объявление «принадлежит» срезу, а в настоящей категории считается
«знакомым» → её `new_per_day` занижается. Правка: `categories.kind` (`category` | `query`); объявления, впервые
увиденные в срезе, получают `ads.query_id`, а `category_id` назначается только из настоящей категории; при подсчёте
«новых» для настоящей категории объявление без `category_id` считается новым.

## 3. Ценовой фильтр (TICKET)

В выдаче уже стоит `pmin=10 000`, поэтому все доли считаются внутри сегмента ≥ 10 000 ₽.

| Поле | Смысл |
|---|---|
| `price_p50`, `price_p75` | по свежим (7 дн) объявлениям |
| `share_ge_20k`, `share_ge_30k` | доля свежих объявлений не дешевле 20 / 30 тыс. ₽ |

**Проход** (стартовые значения, подстраиваются по первым данным — см. ниже):
`price_p75 ≥ 25 000` **или** `share_ge_20k ≥ 30%` **или** `share_ge_30k ≥ 15%`.

Т.е. категория с дешёвой медианой проходит, если в ней есть заметный дорогой подрынок. Провал — только когда
дорогих объявлений почти нет по всем трём признакам. Даже провал по чеку — не навсегда: категория попадает в
ротацию EXPLORE (раз в 14 дн), не в вечный LOW.

Пороги уточняются после первого обхода: в отчёт дня 1 выводится распределение `p75` и `share_ge_20k` по 209
категориям, и пороги ставятся так, чтобы отсечь явный «дешёвый хвост» (ожидаемо 25–40% категорий).

## 4. Турнир (successive halving)

Идея: слабая категория не должна набрать 15 замеров, если после 4–6 видно, что она сильно уступает. Карточки —
только из объявлений, которые уже есть в `ads` (выдачу перечитывать не нужно): возраст 1–4 дня, цена ≥ 10 000,
разные города/магазины, случайно.

### Stage 0 — дешёвые признаки (все 209 категорий + 48 срезов)

Только выдача. Из 209 категорий исключаются из турнира (→ EXPLORE с причиной, перепроверка по ротации):
- TICKET не пройден (§3);
- мёртвый рынок: `new_per_day` < 2 при `conf_supply` ≥ MEDIUM;
- **жёсткая** концентрация — только если **одновременно**: `top_shop_share` > 60% **и** `cities_per_100` < 5 **и**
  `models_repeated` < 2.

Остальные ранжируются **дешёвым рейтингом** (только чтобы выбрать, кому дать первые карточки):

```
cheap = rank(log new_per_day) + rank(share_ge_20k) + rank(models_repeated) + rank(cities_per_100)
        − concentration_penalty          # 0, если top_shop_share ≤ 30%; линейно до 1 ранга при 80%+
```
Топ **K1 ≈ 36** → Stage 1. (K1 подбирается так, чтобы Stage 1 укладывался в ~70 карточек/день.)

### Stage 1 — грубый спрос: 2 карточки × 2 дня = 4 замера на категорию

Оценка категории: `D = median(vpd)` её замеров. Поле: медиана `D` среди всех участников стадии = `M`.

**Выбывает** (→ EXPLORE, «выбыла на Stage 1», повтор не раньше чем через 21 день), если **все**:
- `D` в нижней половине поля;
- `D < 0.6 × M` (явно слабее, а не «чуть ниже»);
- лучший замер `max(vpd) < M` (ни одно объявление не дотянуло до типичного уровня поля — защита от шума малой выборки).

Иначе — проходит. Ожидаемо проходят ~50–60% → **K2 ≈ 18–22**.

### Stage 2 — уточнение: 4 карточки × 2 дня (итого 12 замеров)

Теперь `D = median(vpd)`, `D75 = p75(vpd)`, плюс разнообразие продавцов по карточкам.

**Выбывает** (→ WATCH_PROVISIONAL, не в EXPLORE: она уже прошла один отсев), если:
- `D` ниже 40-го процентиля поля Stage 2 **и** `D75` ниже медианы поля по `D`, **или**
- в выборке ≤ 3 разных продавцов из 12 (рынок одного-двух продавцов) **и** `models_repeated` < 3.

Проходят ~55–65% → **K3 ≈ 10–14**.

### Stage 3 — подтверждение: 4 карточки × 2 дня (итого 20 замеров) + проверка устойчивости

Финалисты получают выборку, достаточную для `conf_demand` = HIGH на текущий момент, и проверку устойчивости:
медиана по первым 10 замерам против последних 10 (не упала ли вдвое).

### Ранжирующая функция между стадиями (объяснимая)

Сортировка по `D` (медиана vpd), при близких `D` (±15%) — по `attention_per_listing`, затем по `models_repeated`.
Каждое решение пишется в `tier_events` текстом, например:
- «Stage 1 → прошла: медиана 23/д (поле 11/д), лучший 140/д, 4 замера»;
- «Stage 1 → выбыла: медиана 4/д < 0.6 × 11/д, лучший 8/д < 11/д, 4 замера»;
- «Stage 2 → выбыла: медиана 7/д (40-й проц. поля 12/д), p75 10/д < 15/д».

## 5. Итоговые tiers и точные условия

### CORE_PROVISIONAL (день ~8)

Финалист Stage 3, у которого **все** условия минимального бизнес-качества (не «топ X%»):

| Условие | Стартовое значение |
|---|---|
| спрос | `vpd_p50` ≥ **10/д** **и** ≥ медианы финалистов |
| устойчивость | медиана последних 10 замеров ≥ 0.5 × медианы первых 10 |
| чек | TICKET пройден (§3) |
| повторяемость | `models_repeated` ≥ 3 **или** `model_share` ≥ 25% |
| независимость | ≥ 6 разных продавцов из 20 замеров **и** `top_shop_share` ≤ 60% |
| уверенность | `conf_demand` ≥ MEDIUM (n ≥ 15), `conf_supply` ≥ MEDIUM |

Не прошёл хотя бы одно → **WATCH_PROVISIONAL** с указанием, что не прошло.
CORE не дополняется до квоты: сильных 6 — CORE = 6. Если прошло больше `CORE_MAX` (15) — лучшие по
`vpd_p50 × attention_per_listing` остаются, остальные → WATCH.

Пороги «10/д», «6 продавцов», «3 модели» — стартовые; после турнира в отчёт выводится распределение по финалистам,
пороги корректируются один раз по данным (ADR).

### Взросление (дни 14–30)

`*_PROVISIONAL` → `CORE` / `WATCH` (mature), когда у категории ≥ 14 дней наблюдений, n ≥ 30 замеров, условия CORE
держатся ≥ 70% пересчётов за последние 7 дней. Дальше работает гистерезис:

| Переход | Условие |
|---|---|
| WATCH → CORE | все условия CORE **3 пересчёта подряд** |
| CORE → WATCH | `vpd_p50` ниже **медианы** CORE+WATCH (вход был — верхняя половина финалистов) **5 пересчётов подряд**, и ≥ 7 дней в CORE |
| WATCH → EXPLORE | спрос ниже 40-го процентиля WATCH **7 пересчётов подряд** |
| EXPLORE → турнир | ротация нашла рост (z ≥ 2 по предложению или спросу) или прошло 21 день после выбывания |
| LOW_PRIORITY | только категория, выбывшая из турнира **дважды**, или провал TICKET на двух проверках подряд; перепроверка раз в 30 дней |

## 7. Сроки

- **Первый шорт-лист** (CORE_PROVISIONAL / WATCH_PROVISIONAL, уверенность MEDIUM): утро **дня 8** обходов.
  День 1 — первый полный обход (ожидаемо 05.10, если не помешают блоки); шорт-лист ≈ **12.10**.
- **Зрелый рейтинг** (HIGH): дни 14–30.
- Блоки сдвигают график: стадия не закрывается, пока у участников нет нужного числа замеров (стадия ждёт, а не
  решает по неполным данным).

## 8. DB changes

```sql
ALTER TABLE categories ADD kind TEXT DEFAULT 'category';     -- category | query
ALTER TABLE categories ADD tier TEXT DEFAULT 'EXPLORE';      -- CORE[_PROVISIONAL] | WATCH[_PROVISIONAL] | EXPLORE | LOW_PRIORITY | QUERY_WATCH
ALTER TABLE categories ADD stage INTEGER;                    -- 1..3 в турнире, NULL вне его
ALTER TABLE categories ADD tier_since DATE;
ALTER TABLE categories ADD tier_reason TEXT;
ALTER TABLE categories ADD streak_up INTEGER DEFAULT 0;
ALTER TABLE categories ADD streak_down INTEGER DEFAULT 0;
ALTER TABLE categories ADD eliminated_at DATE;
ALTER TABLE categories ADD eliminations INTEGER DEFAULT 0;
ALTER TABLE categories ADD last_explored_at TIMESTAMP;
ALTER TABLE ads ADD query_id INTEGER;                        -- первый срез, где видели (category_id — только настоящие)
ALTER TABLE scan_categories ADD promo_seen INTEGER;

CREATE TABLE category_metrics (category_id, day, <поля §1, §3>, PRIMARY KEY (category_id, day));
CREATE TABLE tier_events (id INTEGER PRIMARY KEY, category_id, day, old, new, stage, reason);
```
`card_obs.bucket`: `baseline` (турнир и база категорий), `liquidity` (перепроверка финалистов).
