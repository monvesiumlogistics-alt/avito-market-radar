# Avito rate limits: исследование

Дата: 2026-10-04. Статус: исследование, код не менялся (после ADR-018). Дизайн — `docs/avito-traffic-v2.md`.
Цель — **максимум рыночной информации на минимум загрузок**, капча только руками человека, устойчивое продолжение
после блоков. Обход защиты (решатели капчи, подмена TLS/отпечатка, ротация IP) — вне рамок (ADR-005).

Метки: **[ФАКТ]** — код/БД/лог/источник; **[ОЦЕНКА]** — расчёт; **[МНЕНИЕ]** — инженерная позиция.

Выводы:
1. **~830 загрузок за ~2 часа (прогоны 4–5) → IP в лимите ~6 часов** (439 c 20:30 до 00:52).
2. **На следующий день блок пришёл уже через ~60 загрузок при темпе 3/мин.** Значит, лимит — не только «запросы в
   минуту»: у адреса есть **память/репутация за часы–сутки**. [ОЦЕНКА] Решают суточный объём и паузы на восстановление,
   а не только задержка между страницами.
3. `/report` стабильно тратит **~17.5 загрузок на подкатегорию** (373/22, 212/12, 228/13): ~11 карточек (63%), ~5
   страниц выдачи, ~0.5 профиля, накладные.
4. В sweep 18 из 20 категорий упёрлись в лимит глубины, средний `total_count` ≈ 115 000 — **категории огромные**,
   инкрементальный стоп «дошли до знакомого» в них не наступает никогда.

## 2. Current request flow (кто и где делает навигацию)

```
Telegram /report ─┐                              ┌─ APScheduler 09:00 / catch-up / /sweep
                  ▼                              ▼
          MarketCrawler.start(kind) ── task _run ── gate.acquire (BrowserGate)
                  │
                  ├─ _open_provider → AvitoBrowserProvider.__aenter__ (launch_persistent_context; без навигации)
                  │      повтор через 2 с при ошибке (m10)
                  ├─ [report] _recheck_finds: ≤ RECHECK_MAX(20) карточек находок 2–14 дн      → goto ×≤20
                  ├─ [report] discover_sections: страница раздела, если карта старше 30 дн      → goto ×0–25
                  ├─ [report] _crawl_all → crawl_subcategory:
                  │      _collect: выдача ?s=104&pmin, до 7 дн или REPORT_MAX_PAGES(5)            → goto ×1–5
                  │      _evaluate: ≤2 карточки на группу, ≤12 на подкатегорию                     → goto ×≤12
                  │      _seller_date: профиль продавца для кандидата с vpd ≥ 50                   → goto ×0–N
                  └─ [sweep] _sweep_all → _collect(max_pages=plan_depth, known_stop)             → goto ×2–10

Каждая загрузка: MarketCrawler._fetch → _before_load (стоп, бюджет, уступка браузера, [sweep] пауза 10±5 с)
   → AvitoBrowserProvider.fetch:
        new_page()                                     (вкладка; сетевой навигации нет)
        if not _warmed: goto(главная) + 2 с            (WARM-UP: +1 навигация на сессию браузера)
        sleep(PAGE_DELAY_MIN..MAX = 4..9 с из .env)
        goto(url, domcontentloaded) + wait_for_selector(≤15 с)
        content(), title(); close()
        блок? (403/429/439 или маркеры) → dump HTML → ProviderBlocked

ProviderBlocked в _fetch:
   _wait_for_human: Telegram «🧩» → provider.wait_unblocked:
        new_page() + goto(ЗАБЛОКИРОВАННЫЙ url)         (+1 навигация прямо во время блока)
        опрос DOM раз в 5 с без перезагрузки, до CAPTCHA_WAIT_MINUTES(15)
   пройдено → СРАЗУ повтор goto(url)                   (без остывания)
   не пройдено → [ADR-018] пауза 60/120/240 мин → повтор; счётчик пауз НА ОДНУ СТРАНИЦУ

Scanner (мониторинг, APScheduler каждые 60 мин; правило сейчас выключено):
   gate.hold() → если идёт MarketCrawler: gate.contended → _handover:
        закрыть Chromium → отдать замок → Scanner открывает СВОЙ браузер (delay=(0,0)!) → warm-up + до 3 стр./URL
        → MarketCrawler снова открывает браузер → ещё warm-up
```

## 4. Root causes

| # | Причина | Доказательство | Вес |
|---|---|---|---|
| R1 | **Суточный объём** — /report + sweep легко дают 1 000–2 500 навигаций в сутки с одного IP | журнал прогонов; блок на 2-й день при 3/мин | главный |
| R2 | **Пачки**: 600 загрузок за ~1 час без перерыва | прогон 4 → блок в прогоне 5 | высокий |
| R3 | **Полный обход огромных категорий**: смысл «дочитать до вчерашнего» в категории с ~10 000 новых/сутки отсутствует, а формула глубины тянет к 10 стр. | 18/20 depth_cap, total ≈ 115k | высокий (новое, после ADR-016) |
| R4 | **Карточки — 63% загрузок /report**, по 12 на подкатегорию, без общего дневного бюджета | 11.2 открытых в среднем (прогон 5) | высокий |
| R5 | Нет остывания после капчи: повтор сразу, на «горячем» адресе | `_fetch` | средний |
| R6 | Нет лимита блоков на прогон/сутки: пауза считается на одну страницу, следующая страница снова начинает с 0 | `_fetch` (ADR-018) | средний |
| R7 | Ожидание капчи делает `goto` заблокированного URL в новой вкладке | `wait_unblocked` | низкий |
| R8 | Scanner вытесняет прогон: перезапуск браузера + 2 warm-up + страницы без задержки | `_handover`, `Scanner(delay=(0,0))` | низкий сейчас (правило выключено), высокий при включении |
| R9 | Перепроверка 20 находок в начале **каждого** нажатия /report | `_recheck_finds` | низкий–средний |
| R10 | Профиль продавца ради точной даты для каждого кандидата ≥ 50 vpd | 12 профилей на 35 находок | низкий |

Что **не** причина [МНЕНИЕ, по коду]: новая вкладка на каждый fetch (сетевых запросов не добавляет: кэш и cookies
общие у контекста), warm-up (1 навигация на сессию; лишними становятся только при переоткрытии браузера).

## 7. Rate limiting approaches considered

| Подход | Для 1 пользователя / 1 IP / 1 Chromium | Вердикт |
|---|---|---|
| Фиксированная задержка | просто, но пачки по 600 всё равно возможны | база |
| + случайный разброс ±50% | убирает метрономный ритм | **да** |
| Token bucket (ёмкость > 1) | разрешает всплески — **нам всплески как раз вредят** | нет |
| Leaky bucket = минимальный интервал между навигациями | ровный поток | **да (ёмкость 1 = «не чаще раза в N с»)** |
| Скользящее окно (≤ X за час) | ограничивает часовой объём — именно то, что видит Avito | **да, как второй предохранитель** |
| AutoThrottle по latency | у нас один поток, latency мало говорит о лимите Avito | нет |
| Адаптивный: ускоряться после N успешных | рискованно: репутация IP копится часами | **нет ускорения ниже базового интервала**; только замедление |
| Экспоненциальный бэкофф после блока | — | **да** (уже ADR-018, нужно на уровне прогона/суток) |
| Cooldown после капчи + slow mode | после «пройдено» адрес ещё под наблюдением | **да** |
| Circuit breaker | 3 блока за прогон/сутки → стоп до завтра | **да** |
| Дневной бюджет | главный рычаг (R1) | **да** |

**Выбор [МНЕНИЕ]:** «leaky bucket ёмкостью 1» (минимальный интервал + разброс) + часовое окно + дневной бюджет +
замедление после блока, восстановление постепенно (как Googlebot), ускорения выше базы нет.

## 8. Incremental crawling approaches

| Эвристика | Плюсы | Минусы | Вердикт |
|---|---|---|---|
| Стоп на первом известном id | — | промо/поднятия → ранний стоп | нет |
| N подряд известных | просто | одно «поднятое» ломает серию | как доп. сигнал |
| **Доля известных на странице ≥ 0.85** (сейчас) | устойчиво | в огромной категории не наступает | **да, для малых/средних** |
| Водяной знак id | — | **опровергнут**: id ≠ время (ADR-015) | нет |
| Граница «вчера» по дате выдачи | бесплатно | дата — день, «Вчера» | как доп. стоп |
| **Выборочный режим для огромных категорий** | 1 страница даёт `total_count` + плотность (темп) + свежие модели | не видим все новые | **да — главное исправление R3** |
| Оценка темпа → глубина | меньше лишних страниц | нужна история | **да, но с потолком по классу категории** |

Классы категорий по темпу (новых в сутки, из истории; без истории — по `total_count`):

| Класс | Темп | Режим | Страниц/день |
|---|---|---|---|
| quiet | < 25 | инкремент, раз в 2 дня | 0.5–1 |
| normal | 25–150 | инкремент до «знакомых» | 1–4 |
| **large** | > 150 (или `total_count` > 20 000 без истории) | **выборка**: только стр. 1 (свежие модели + `total_count` + плотность) | **1** |

Глубина для normal: `pages = ceil(rate × hours_since / 50 × 1.3) + 1`, потолок 4 (дальше категория — large).

## 9. Block/CAPTCHA lifecycle

```
           ok                      блок (403/429/439/маркеры)
NORMAL ─────────▶ NORMAL ───────────────────────────────────────▶ BLOCKED
  ▲                                                                  │ навигации стоп (все: sweep, report, scanner)
  │ 2 ч без блоков: интервал ÷1.5 (не ниже базы)                     │ Telegram «🧩 …нажми "Продолжить" и пройди капчу»
SLOW (интервал ×2) ◀── COOLDOWN 5 мин без навигаций ◀── пройдено ── WAIT_HUMAN (тот же таб, опрос DOM, без reload,
  │                                                                  │            ≤ 15 мин)
  │ блок                                                             │ не пройдено
  ▼                                                                  ▼
BLOCKED ... ─────────── 3-й блок за сутки ─────────────▶ HALTED_TODAY  ◀── PAUSE 60/120 мин (без навигаций) ── блок снова
                       (прогон сохранён, «продолжу завтра / по команде»)
```

- «Продолжить» на странице блока **нажимает человек**. Автонажатие сэкономит один клик, а человек всё равно нужен
  для капчи; это уже взаимодействие с защитной страницей → не делаем [МНЕНИЕ].
- Ожидание — **на той же вкладке**, где появился блок, без `goto`/reload: опрос `content()/title()` раз в 5 с.
- После «пройдено» — **5 мин без навигаций**, затем SLOW (интервал ×2) минимум на 2 часа.
- Лимиты: `MAX_BLOCKS_PER_DAY = 3` → HALTED до следующего дня (или `/sweep` вручную).

## 10. Recommended architecture

Один небольшой **`AvitoTraffic`** (в `app/providers/traffic.py`) вместо разбросанных задержек/бюджетов:
единственная точка «можно ли сейчас навигацию на Avito и когда». Через него ходят MarketCrawler (sweep, deep,
report, recheck) и Scanner. Состояние (блоки за сутки, slow mode до, дневные счётчики по видам) — в SQLite, чтобы
переживать рестарт. Подробно — `docs/avito-traffic-v2.md`.

Плюс изменения логики объёма: выборочный режим огромных категорий, общий дневной бюджет карточек, профили — только
для кандидатов отчёта, перепроверка — по расписанию и только ценного, Scanner не вытесняет прогон.

| Ожидание капчи | +1 goto на блок | 0 |
| **Итого** | **~4 500 (report) или ~2 500–3 000 (sweep+report)** | **≈ 430–470** |

Сокращение ≈ **6–10×**. При интервале ~45 с это ≈ 5–6 часов фоновой работы в сутки — растягиваем, а не жмём.

## 12. Risks

| Риск | Митигация |
|---|---|
| Даже 450/сутки окажется много для этого IP | телеметрия + дневной бюджет в `.env`; снижение до 300 без изменения кода |
| Выборка в крупных категориях пропустит редкие модели | частые модели появляются на стр. 1 ежедневно; редкое ловит deep scan по моделям |
| Медленный обход не успевает к утру | старт 06:00–07:00 (если ПК включён) или радар «по готовности»; частичный радар с покрытием |
| Человека нет при капче | HALTED_TODAY вместо бесконечных попыток; данные сохранены |
| IP помечен надолго | обращение в поддержку Avito (IP, провайдер) — по их же рекомендации; сторонний API выдачи как запасной вариант |

## 14. Implementation plan

См. `docs/avito-traffic-v2.md` §9 (по файлам). Порядок: (1) выборка крупных категорий — сразу убирает самый большой
перерасход; (2) `AvitoTraffic` (интервал, час, сутки, состояния, лимит блоков); (3) ожидание капчи на той же вкладке +
cooldown/slow; (4) Scanner не вытесняет прогон; (5) общий бюджет карточек, профили и перепроверка по правилам;
(6) телеметрия по видам загрузок.

## «Что мы сейчас делаем неправильно» (проверено по коду и журналу)

1. **Жмём объём, а не темп**: 600 загрузок за нажатие, несколько нажатий подряд; суточного лимита нет.
2. **Крупные категории обходим «до знакомого»**, которого там не бывает → потолок глубины каждый день.
3. **Карточки без общего бюджета**: по 12 на подкатегорию независимо от ценности.
4. **После капчи — сразу в бой**, без остывания и замедления.
5. **Счётчик блоков на страницу**, а не на прогон/сутки — возможна длинная серия «пауза → блок → пауза».
6. **Ожидание капчи стучится в заблокированный URL** ещё раз.
7. **Scanner вытесняет прогон** и ходит без задержки (сейчас неактивен — правило выключено).
8. **Перепроверка 20 находок на каждом нажатии** /report.
9. **Профили продавцов для всех кандидатов**, не только для попадающих в отчёт.

Что делаем **правильно** и не трогаем: один браузер и `BrowserGate`, постоянный профиль, ручная капча, запись после
каждой страницы, чекпойнт sweep по страницам, история `ads`, warm-up один раз на сессию.
